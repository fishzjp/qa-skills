01 · Why

软件发布之前，
总得有人先把住质量关

每一款软件上线前，都要回答成百上千个「如果」： 并发下单会不会超卖？优惠券到期会不会自动失效？接口异常时数据会不会错乱？

干这件事的，是软件测试工程师： 在缺陷到达用户之前发现它、定位它，再确认它被修好。

qa-skills 做的，就是让 AI 助手学会这套本事。

上线前要回答的问题
并发下单 ··· 高峰期会不会超卖？
优惠券到期 ··· 失效有没有空窗期？
接口重试 ··· 会不会重复扣款？
权限变更 ··· 旧会话还能不能用？
历史回归 ··· 修好的缺陷会不会复发？
02 · Problem

能写，更要能执行。

通用大模型写出的用例，常常看着专业、实际没法执行：
判定模糊、占位符没替换、时限没说清、入口是编的。
这是能力问题，更是纪律问题。

✗ 无 Skill 的模型产出 CASE-001

判定模糊，无法执行

预期结果不可判定，等于没有验证：

「检查优惠券功能是否正常」
「正常」是什么标准？谁判定？等多久算超时？

判定不了的用例，覆盖再全也计零分。

✓ qa-skills 的真实产出 TC-03-05

步骤精确，判定可量化

前置、步骤、预期、时限，四要素齐备：

「选一张 10 分钟后到期 的已发布优惠券，等待到期。
预期：1 小时内状态自动变为「已结束」，
超过 1 小时即判失败。」

任何测试人员拿到就能执行，不用讲解。

产出标准只有一条：
任何一个没接触过这个需求的人，拿到文件就能直接执行。 背后是 8 条可执行性硬标准，评测中一票否决。

05 · Skills

从用例到回归，
每道工序都有对应的 Skill。

每个 Skill 单独可用，也能串成完整流水线。需要哪一段，就用哪一段。

test-case-writing01

用例设计

代码优先：先读实现、审出潜在缺陷，再落笔。产出两份，markmap 脑图给人读，schema.yaml 给机器校验。

test-strategy02

测试策略

风险评级必须给出证据；性能、安全、并发等十个类型，逐一决定测还是不测，每个决定都留下记录。说不清依据的策略，等于没有策略。

test-case-review03

用例评审

把所有能测的点列全，作为基准逐条复审：覆盖够不够、能不能执行，直接修订文件并留下审查记录。

automated-e2e · api-testing04

自动化执行

用例转成可运行的 Playwright / pytest 代码：按 Page Object 规范组织，测试数据自己造、跑完自己清。

bug-analysis05

缺陷分析

先复现，再读代码定位到出错的那一行，然后分析影响面、给出回归建议。产出的 Bug 条目带根因、带证据。

regression-testing06

回归测试

从代码改动推算波及范围，生成回归清单。防止修一个、坏三个。

07 · Install

两步接入你的 AI 助手

不需要账号，不需要订阅。两条命令，一句话。

01

把 Skill 装进 AI 编程助手

终端里执行（macOS / Linux），也可以按 README 手动复制文件：

$ git clone https://github.com/fishzjp/qa-skills.git
$ cd qa-skills && ./install.sh
# 选择装到哪个助手，或 ./install.sh --auto 全自动

用 DeepSeek Harness（dsh）？插件已上架 npm，一条命令装好：

$ dsh plugin --profile web add dsh-qa-skills
02

对 AI 助手说一句话

像给测试同事派活一样：

你，对 AI 助手说
「帮我测试这个需求：{需求描述 + 仓库地址}」

需求分析、测试策略、用例设计、评审、执行、缺陷分析、回归与报告， 流水线就此跑通。只需要其中某一步，直接说需求就行，不必走全流程。
