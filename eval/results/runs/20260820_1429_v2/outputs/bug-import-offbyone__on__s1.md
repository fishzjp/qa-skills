### BUG-2077: 批量导入优惠券失败行的行号提示错位一行

- **严重程度**: P2
- **现象**: 管理后台批量导入优惠券 CSV，校验失败行的错误提示行号总比实际行号大 1。
- **复现步骤**:
  1. 准备 CSV：第 1 行表头，第 2 行合法数据，第 3 行面额=5000（非法），第 4 行合法数据
  2. 后台 → 券工场 → 批量导入，上传该文件
  3. 导入结果提示"成功 2 条，失败 1 条：第 4 行：面额需为 1-1000"
- **Root Cause**: `importer.py` L31 `line_no = reader.line_num + 1` 多加了一行。`csv.DictReader.line_num` 返回的是**源文件的物理行号**（1-based，含表头行），已经与 CSV 实际行号一致。表头在第 1 行时，`DictReader` 读取表头后 `line_num=1`；读取第 2 行数据时 `line_num=2`，第 3 行数据时 `line_num=3`。L31 再 `+1` 导致第 3 行被报告为第 4 行。同函数 L34 的通用异常分支 `line_no = reader.line_num`（无 `+1`）反而是正确的，两处存在不一致。[Verified]（复现步骤已验证现象，代码行已定位）
- **Evidence**:
  - E3：Bug 报告复现结果——CSV 第 3 行面额=5000，导入提示"第 4 行"（staging-2，Chrome 120）
  - E2：`importer.py:31` — `line_no = reader.line_num + 1`（`ValidationError` 分支，多余 `+1`）
  - E2：`importer.py:34` — `line_no = reader.line_num`（通用 `Exception` 分支，无 `+1`，行为正确，佐证 L31 的 `+1` 是错误来源）
  - E2：Python 标准库 `csv.DictReader.line_num` 语义——返回已从源迭代器读取的行数，含表头行
- **影响范围**:
  - **功能面**：所有触发 `ValidationError` 的导入失败行均受影响——`validate_coupon` 中的两条校验路径："面额需为 1-1000"（`importer.py:47`）和"使用门槛不能低于面额"（`importer.py:49`）报错时行号均偏移 +1。来源：L31 是唯一的 `ValidationError` 行号计算点。
  - **功能面（不一致风险）**：通用 `Exception` 分支（L34，如 `IntegrityError` 名称冲突、`parse_coupon` 中的 `int()` 转换异常）使用 `reader.line_num`，行号正确。同一导入结果中若同时存在 `ValidationError` 和 `Exception` 两类失败，行号体系不一致，进一步误导排查。来源：L31 vs L34 对比。
  - **数据面**：无脏数据产生。校验失败的行未调用 `save_coupon`，仅行号展示错误。来源：L28 `validate_coupon` 在 L29 `save_coupon` 之前执行。
  - **用户面**：所有通过管理后台使用"券工场 → 批量导入"功能的管理员用户。来源：Bug 报告环境描述。
- **Severity 依据**: 功能可用（导入正常完成，成功/失败计数正确），仅失败行号偏移导致排查误导——属体验问题，定 P2。与 Bug 报告评级一致。
- **修复建议**: 将 L31 改为 `line_no = reader.line_num`（去掉 `+1`），与 L34 通用异常分支保持一致。建议同步审查 L31 与 L34 的行号计算逻辑，提取为同一变量或调用统一函数，消除两处分别维护的不一致风险。
- **回归建议**:
  - **直接复现用例**（建议新增 TC-IMP-021）：CSV 第 1 行表头 + 第 2 行合法 + 第 3 行面额超限 → 断言提示"第 3 行"。
  - **边界用例**（建议新增 TC-IMP-022）：失败行出现在首条数据行（CSV 第 2 行）和末行，验证行号正确。
  - **多错误用例**（建议新增 TC-IMP-023）：同一 CSV 含多个 `ValidationError` 失败行，验证每个行号均正确。
  - **混合异常用例**（建议新增 TC-IMP-024）：同一 CSV 同时含 `ValidationError`（校验失败）和 `Exception`（如名称冲突 / 非数字字段）失败行，验证两类错误的行号体系统一且正确——此用例专门覆盖 L31 与 L34 的一致性。
  - **关联回归**：导入全部成功的正常路径用例（无行号输出，不应受影响）；导入含空行 / 含逗号转义字段的 CSV，验证 `line_num` 语义在复杂 CSV 格式下仍正确。

## 待澄清清单

1. **`csv.DictReader` 对多行记录的支持**：若 CSV 字段内含换行符（引号包裹的多行字段），`line_num` 的语义会跨越多物理行。当前分析基于标准单行记录假设；如业务允许字段内换行，需确认行号展示口径（物理行 vs 逻辑记录序号）。
2. **前端展示链路**：Bug 报告仅给出后端返回的错误信息文本，未提供前端渲染逻辑。分析假定后端返回的行号即前端展示行号，无前端二次偏移。若前端对行号另有处理，需补充前端代码确认。
