# 余额转账功能测试策略

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 功能名称 | 余额转账（站内用户间实时转账） |
| 被测分支 | backend repo / feature/transfer |
| 核心模块 | transfer_service.py、余额服务、风控服务、消息通知 |
| 产出物 | 测试策略文件（本文） |
| 备注 | 不包含具体测试用例；具体用例由本策略派生 |

## 2. 测试目标

- 验证余额转账在正常路径、边界、异常路径下的功能正确性。
- 重点验证无分布式事务下的资金一致性、幂等性、限额控制、风控状态机正确性。
- 暴露代码走读中已识别的高风险缺陷，并给出可观测的验证手段。
- 建立回归基线，防止重构或补偿逻辑变更引入资金类故障。

## 3. 测试范围

### 3.1 范围内

- 发起转账：金额校验、余额校验、限额校验、备注校验。
- 风控路径：大额触发审核、异步回调、超时放行、审核拒绝。
- 资金流转：发起方扣款、收款方加款、冻结、回滚/补偿。
- 状态机：转账单状态流转（发起 → 风控审核/直接成功 → 成功/失败）。
- 幂等与重复：重试、并发、单号重复。
- 通知：消息通知触发时机与内容。
- 依赖异常：余额服务、风控服务、消息通知的失败与降级。

### 3.2 范围外

- 用户注册/登录/KYC 流程。
- 账户余额充值、提现、消费。
- 风控模型本身的准确率评估（仅验证集成行为）。
- 前端 UI 交互测试（仅做接口层契约验证）。

## 4. 风险地图（Risk Map）

### 4.1 风险分级说明

- **P0（致命）**：资金丢失、资金凭空增加、重复扣款、安全可被利用。
- **P1（严重）**：状态不一致、限额被绕过、风控被绕过、补偿失效。
- **P2（中等）**：精度误差、缓存短暂偏差、通知缺失、可恢复异常。
- **P3（轻微）**：文案、日志、可观测性不足。

### 4.2 风险矩阵

| 编号 | 风险类别 | 风险描述 | 根因/出处 | 等级 | 影响 | 测试关注点 |
|---|---|---|---|---|---|---|
| R-01 | 资金一致性 | 三步（扣款→风控→加款）无分布式事务，任一步失败靠补偿回滚，补偿不全或失败将导致资金不一致 | 代码走读 | P0 | 发起方扣款但收款方未加款（资金丢失）；或加款后未扣款（资金凭空增加） | 验证每一步失败时的补偿路径；补偿自身失败的兜底；资金对账脚本 |
| R-02 | 幂等性 | 转账请求无幂等键，网络重试会产生重复转账单 | 代码走读 | P0 | 重复扣款/重复加款/重复风控 | 客户端重试、网关重试、MQ 重投场景下的重复单检测 |
| R-03 | 单号唯一性 | 转账单号=时间戳+随机数，无唯一约束，高并发或低概率随机碰撞会生成相同单号 | 代码走读 | P0/P1 | 单号冲突导致数据错乱、重复入账或唯一性破坏 | 高并发下单号碰撞验证；DB 层唯一约束缺失的回归 |
| R-04 | 金额精度 | 中间计算用 float，仅入库前转 Decimal，浮点误差可能导致比较与计算偏差 | 代码走读 | P1 | 余额比较误判、累计金额偏差、显示异常 | 多笔小额累加、0.1+0.2 类经典场景、边界金额比较 |
| R-05 | 限额控制 | 日累计从本地缓存读取，30 秒刷新，短时内多笔转账可绕过日累计限额 | 代码走读 | P1 | 用户在 30 秒内多笔转账突破 20000 元日限额 | 缓存窗口内的并发转账；缓存过期瞬间的并发；缓存与 DB 偏差 |
| R-06 | 风控绕过 | 风控回调超时 10 分钟自动放行，可能被利用绕过风控 | 代码走读 | P1 | 大额或异常资金通过超时机制逃避审核 | 超时放行路径；超时期间的人工拒绝优先级；风控不可达时的行为 |
| R-07 | 状态机 | 状态机含异步分支（风控回调），并发回调/重复回调可能导致状态跳跃或回退 | 需求+代码 | P1 | 已成功单被回滚为失败；已失败单被重复加款 | 重复回调、乱序回调、回调与超时放行竞态 |
| R-08 | 并发扣款 | 余额扣减与并发转账无显式锁/版本号说明，可能透支 | 代码推断 | P0 | 余额不足但因并发校验通过而扣款成功（透支） | 同一发起方高并发多笔转账；余额临界值并发 |
| R-09 | 大额冻结 | 大额审核中资金冻结，但冻结与扣款的关系不清晰，可能冻结失败仍扣款 | 需求+代码 | P1 | 用户余额被错误冻结或冻结金额不正确 | 冻结金额=转账金额；冻结期间可用余额；解冻路径 |
| R-10 | 补偿幂等 | 补偿逻辑（回滚加回余额）若幂等缺失，重复补偿会多加余额 | 代码走读 | P0 | 补偿重复执行导致资金凭空增加 | 补偿逻辑重复触发；补偿与正常路径并发 |
| R-11 | 通知一致性 | 消息通知与资金操作非原子，通知失败或早于落库可能导致用户误判 | 需求 | P2 | 用户收到通知但资金未到账，或反之 | 通知时机；通知失败的重试；通知与最终一致性 |
| R-12 | 边界输入 | 金额保留 2 位小数，但输入未明确校验负数、0、超长小数、字符串注入 | 需求 | P1 | 非法金额绕过校验导致逻辑异常 | 负数、0、0.001、9999.999、科学计数法、字符串 |
| R-13 | 备注注入 | 备注 ≤ 50 字，但未提及字符类型与转义，可能存在 XSS/SQL 注入 | 需求 | P2 | 前端展示 XSS 或日志注入 | 多字节字符、emoji、HTML/JS 片段、超长 UTF-8 |
| R-14 | 可观测性 | 无分布式事务且补偿异步，缺乏对账与监控将无法发现沉默故障 | 代码走读 | P2 | 资金不一致长期未被发现 | 日志完整性、关键指标告警、对账机制 |
| R-15 | 容灾 | 风控/余额/通知服务不可达时的降级行为未明确 | 依赖 | P1 | 外部依赖故障时转账行为不可预期 | 依赖熔断、超时、重试、人工干预入口 |

## 5. 测试策略分层

### 5.1 单元测试（UT）

**目标**：覆盖 transfer_service.py 的纯逻辑分支与边界。

**重点模块**：
- 金额校验：单笔限额、日累计限额、余额比较、2 位小数处理。
- 状态机：状态流转合法性、非法转移拒绝。
- 单号生成：覆盖时间戳回拨、随机数边界、碰撞概率压力。
- 备注长度计算（含多字节字符）。
- 补偿函数：幂等键、重复执行、失败重试。

**Mock 策略**：余额服务、风控服务、消息通知全部 Mock；重点验证编排逻辑与异常处理。

**准入/准出**：核心分支覆盖率 ≥ 90%；补偿路径 100% 覆盖；0 P0/P1 缺陷遗留。

### 5.2 集成测试（IT）

**目标**：验证 transfer_service 与真实依赖（或契约 Mock）的协作。

**重点**：
- 三步流程的顺序与失败注入：扣款成功/失败、风控调用成功/失败/超时、加款成功/失败。
- 补偿触发条件与补偿完整性：补偿后双方余额回到初始态。
- 风控异步回调：成功、失败、重复回调、乱序回调、超时放行。
- 限额校验与缓存：缓存命中、缓存过期、缓存与 DB 不一致。

**手段**：使用故障注入（依赖超时、返回 5xx、网络中断）、契约测试（Pact 思路）。

### 5.3 接口测试（API）

**目标**：从 HTTP 入口验证契约、参数校验、鉴权、错误码。

**重点**：
- 参数边界：金额（0、负数、非数字、超 2 位小数、单笔 5000、5000.01）、备注（0、50、51、emoji、HTML）、收款方（自己、不存在、被冻结）。
- 鉴权：未登录、token 过期、跨用户操作。
- 重复请求：同一内容多次提交（验证无幂等的实际表现，并作为缺陷记录）。
- 错误码语义与可读性。

### 5.4 端到端测试（E2E）

**目标**：从用户视角验证完整业务路径。

**关键路径（场景维度，非用例）**：
- 小额正常转账：直接成功，双方余额正确，通知送达。
- 大额转账（≥2000）：进入风控审核，资金冻结，审核通过后到账。
- 大额转账被拒绝：资金解冻退回发起方。
- 大额转账超时放行：10 分钟无回调自动成功。
- 余额不足、超单笔限额、超日累计限额的拦截。
- 网络重试下的重复单表现。
- 并发多笔转账的余额与限额表现。

### 5.5 并发与一致性测试

**目标**：针对无分布式事务与缓存窗口的专项验证。

**重点**：
- 同一发起方高并发多笔转账：是否透支、是否超日累计。
- 同一收款方高并发收款：加款是否丢失或重复。
- 补偿与正常路径并发：是否双花。
- 风控回调与超时放行竞态：是否会既回调拒绝又超时放行。
- 单号生成高并发碰撞率压测。

**工具**：JMeter / k6 / wrk + 资金对账脚本。

### 5.6 性能与容量测试

**目标**：验证高峰场景下的稳定性与限额/风控时延。

**场景**：
- 单发起方 TPS 上限与余额一致性。
- 全平台转账 TPS 与风控回调时延。
- 缓存 30 秒刷新窗口下的限额准确性压力。
- 风控服务响应变慢时的雪崩行为。

**指标**：P99 时延、错误率、回调超时率、对账差异率。

### 5.7 安全测试

**重点**：
- 越权：A 用户伪造 B 用户发起/收款。
- 注入：备注字段 XSS/SQL 注入、金额字段类型混淆。
- 重放：截获请求重放（无幂等的暴露面）。
- 风控绕过：构造超时路径逃避大额审核。
- 日志脱敏：是否记录敏感信息。

### 5.8 容灾与可恢复性测试

**重点**：
- 余额服务不可用：转账行为（应失败且不扣款）。
- 风控服务不可用：是否进入超时放行（需业务确认是否符合预期）。
- 消息通知不可用：资金是否仍正确，通知是否补偿。
- 应用重启 / 宕机：补偿任务是否可恢复执行。
- 数据回放与对账：能否发现并修复历史不一致。

## 6. 测试数据策略

- **账户准备**：至少 3 类账户（正常、余额为 0、被冻结），余额覆盖边界值（0、0.01、4999.99、5000、5000.01、19999.99、20000、20000.01）。
- **金额矩阵**：小额、单笔边界 5000、大额 2000 触发点、日累计边界 20000、2 位小数边界、浮点敏感值（0.1、0.2、0.3 累加）。
- **风控数据**：可控制回调结果与回调时延的测试桩账户。
- **并发数据**：专用高并发账户，余额与限额可重置。
- **数据隔离**：测试环境独立账户体系，禁止使用生产数据。
- **数据清理**：每轮执行后重置余额与日累计缓存，避免污染。

## 8. 重点验证清单（场景维度，非用例）

> 以下为高风险场景的验证维度，用于派生具体用例，本身不是用例。

1. **三步失败补偿完整性**：分别在扣款后、风控调用后、加款前制造失败，验证双方余额最终一致。
2. **补偿幂等性**：同一补偿重复执行 N 次，余额不被多加。
3. **重复请求表现**：同一请求连续提交 2~N 次，记录重复单数量与资金影响（预期应识别为缺陷）。
4. **并发透支**：余额 X 时并发发起 N 笔金额 X 的转账，验证不超额扣款。
5. **日累计绕过**：在 30 秒缓存窗口内发起多笔，验证是否突破 20000。
6. **单号碰撞**：高并发下检测单号重复率。
7. **float 精度**：多笔 0.1 元累加并比较余额，验证无误差。
8. **大额风控路径**：2000 元边界、审核通过、审核拒绝、超时放行三路径的资金状态。
9. **超时放行与回调竞态**：超时放行同时收到拒绝回调，验证最终状态唯一。
10. **限额边界**：单笔 5000 与 5000.01、日累计 20000 与 20000.01。
11. **备注边界**：50 字/51 字、emoji、HTML 片段。
12. **依赖熔断**：余额/风控/通知分别不可用时的转账结果。

## 9. 缺陷预防与质量门禁

### 9.1 建议在测试前推动的研发改进（高风险项）

| 建议 | 对应风险 | 优先级 |
|---|---|---|
| 引入幂等键（客户端生成 + 服务端去重） | R-02 | P0 |
| 转账单号改为 DB 唯一约束或雪花算法 | R-03 | P0 |
| 金额全程使用 Decimal，禁止 float | R-04 | P1 |
| 日累计校验改为 DB 实时聚合或分布式计数，缓存仅作辅助 | R-05 | P1 |
| 余额扣减引入乐观锁/版本号/行锁 | R-08 | P0 |
| 补偿逻辑增加幂等标记 | R-10 | P0 |
| 明确超时放行的业务可接受性，必要时改为超时转人工 | R-06 | P1 |
| 建立资金对账机制与告警 | R-01/R-14 | P1 |

### 9.2 质量门禁

- 单元测试核心分支覆盖率 ≥ 90%，补偿路径 100%。
- 集成测试覆盖全部 P0/P1 风险场景。
- 并发与一致性测试：对账差异率为 0。
- 性能：P99 满足约定阈值（待澄清）。
- 安全：无 P0/P1 安全漏洞。
- 0 P0 缺陷遗留；P1 缺陷需有明确缓解措施与上线评审。

## 11. 待澄清清单

1. 转账是否允许向自己转账？是否允许向被冻结账户转账？
2. 日累计限额是按自然日还是滚动 24 小时计算？
3. 日累计是否包含失败/被风控拒绝的转账？仅包含成功的？还是包含审核中的？
4. 大额审核中，发起方能否撤销？撤销后资金如何处理？
5. 风控回调超时 10 分钟自动放行是否符合业务预期？是否需要改为转人工？
6. 风控审核拒绝后，资金是自动退回还是需要人工处理？
7. 单笔限额 5000、日累计 20000 是否包含大额审核中的冻结金额？
8. 转账单号是否计划补建 DB 唯一约束？
9. 是否会引入幂等键？如引入，测试策略中重复请求相关验证需调整。
10. 余额扣减是否已有乐观锁/行锁？代码走读未明确。
11. 消息通知的失败重试次数与最终一致性要求是什么？
12. 性能指标（TPS、P99 时延、回调超时率阈值）是否已定义？
13. 转账是否支持跨币种？当前需求仅提及元，默认单币种。
14. 备注是否需要敏感词过滤？
15. 是否需要对账机制（T+1 或实时）？由谁负责？
