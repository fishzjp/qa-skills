# BUG-2077 根因分析报告

## 1. 根因定位

- **根因描述**：在 `import_coupons` 函数中，捕获 `ValidationError` 时计算错误行号的表达式存在逻辑错误，导致返回的行号总比实际行号大 1。
- **具体代码行**：`importer.py` 第 31 行
- **代码片段**：
  ```python
  line_no = reader.line_num + 1       # L31: line_num 已含表头行，再 +1 多算一行
  ```
- **原理分析**：Python 标准库 `csv.DictReader` 在迭代读取数据行时，其 `line_num` 属性返回的是**当前读取行在整个 CSV 文件中的绝对行号**（包含第 1 行表头）。例如，读取第 3 行数据时，`reader.line_num` 的值即为 3。代码在此正确值的基础上又进行了 `+1` 操作，导致最终提示的行号为 4。同时，第 35 行处理其他异常（`Exception`）时使用的是 `reader.line_num`（无 `+1`），说明 `+1` 属于逻辑写错，而非统一的设计规约。

## 2. 影响范围分析

- **功能影响**：管理后台“券工场 -> 批量导入优惠券”功能中，所有因抛出 `ValidationError`（如“面额需为 1-1000”、“使用门槛不能低于面额”等）导致的失败行，其错误提示行号均会比实际行号偏大 1。
- **连带影响**：
  - 由于代码在处理 `ValidationError` 和 `Exception` 时计算行号的逻辑不一致（一个 +1，一个不 +1），导致系统在不同错误场景下给出的行号提示规则不统一，增加了排查难度。
  - 运营人员或测试人员根据错误提示排查 CSV 数据时会被误导，定位到错误的数据行，降低数据修复效率。
- **数据影响**：无数据层面的破坏，仅影响前端展示的错误信息，导入的成功/失败条数统计不受影响。

## 3. 修复建议

- **修复方案**：将 `importer.py` 第 31 行的 `line_no = reader.line_num + 1` 修改为 `line_no = reader.line_num`，与第 35 行的异常处理逻辑保持一致。
- **修改后代码**：
  ```python
  except ValidationError as e:
      line_no = reader.line_num         # 修复：line_num 已为绝对行号，无需 +1
      results.append(("fail", line_no, str(e)))
  ```

## 4. 回归建议

1. **原 Bug 场景回归**：准备包含 1 行表头 + 2 行合法数据 + 1 行面额非法（如 5000）+ 1 行合法数据的 CSV 文件，验证提示信息是否准确显示为“第 3 行：面额需为 1-1000”。
2. **多错误行场景**：准备包含多行不同类型校验失败（如第 2 行面额超限、第 4 行门槛低于面额、第 5 行发放总量非数字等）的 CSV 文件，验证所有失败行的行号是否与实际文件物理行号完全一致。
3. **系统异常场景回归**：准备会触发系统异常（如数据库唯一索引冲突抛出 `IntegrityError`）的 CSV 文件，验证行号提示是否正确且与 `ValidationError` 的行号规则保持一致。
4. **边界场景回归**：验证无表头 CSV、空 CSV、仅有表头无数据 CSV、首行即出错等边界场景的提示行号是否符合预期。

## 5. 待澄清清单

- 系统内是否有其他模块或外部系统依赖此错误提示的行号（例如历史脚本是否针对此 `+1` 的 Bug 做了偏移适配），需确认修改后是否会产生连带影响。
