# BUG-2077：批量导入优惠券失败行的行号提示错位一行

## 根因分析
在 `coupon-import` 模块的 `importer.py` 文件中，`import_coupons` 函数在捕获 `ValidationError` 异常时，错误地计算了行号。

**根因定位**：`importer.py` 第 31 行
```python
line_no = reader.line_num + 1       # L31: line_num 已含表头行，再 +1 多算一行
```
Python 标准库 `csv.DictReader` 的 `line_num` 属性返回的是当前读取的物理行号（包含表头行）。当循环读取到第 3 行的数据时，`reader.line_num` 的值即为 3。代码在此处又进行了 `+ 1` 操作，导致计算出的行号比实际物理行号大 1。因此，当第 3 行数据发生校验失败时，提示变为了“第 4 行”。

## 影响范围分析
1. **功能影响**：管理后台“券工场 -> 批量导入优惠券”功能。当导入的 CSV 文件中存在业务校验失败（如“面额需为 1-1000”、“使用门槛不能低于面额”等 `ValidationError`）的行时，前端展示及返回给用户的错误提示行号均偏大 1 个行位。
2. **用户体验**：不阻断正常导入流程（合法数据仍可导入成功），但会严重误导运营人员对失败数据行的定位与排查，降低排错效率。
3. **异常处理不一致**：在同模块第 34 行的 `except Exception as e:` 分支中，行号计算使用的是 `reader.line_num`（未加 1），逻辑是正确的。这种不一致会导致当 CSV 中同时存在校验失败和系统错误（如数据库唯一键冲突）时，返回的行号基准不统一。

## 修复建议
修改 `importer.py` 第 31 行，去掉多余的 `+ 1` 操作，使其与第 34 行的行号计算逻辑保持一致：
```python
# 修改前：
line_no = reader.line_num + 1

# 修改后：
line_no = reader.line_num
```

## 回归建议
1. **单元测试补充**：针对 `import_coupons` 方法添加单元测试，覆盖以下场景并断言返回结果中的 `line_no` 准确性：
   - 第 2 行数据校验失败（首行数据报错）
   - 第 3 行数据校验失败（中间行报错）
   - 最后一行数据校验失败（末行报错）
   - 触发 `Exception` 分支的行号准确性验证
2. **接口/功能测试**：在测试环境复现 Bug 报告中的复现步骤，上传包含合法与非法混合数据的 CSV 文件，验证前端展示的错误行号与 CSV 文件物理行号完全对应。
3. **边界测试**：验证空文件、只有表头无数据、连续多行报错等极端情况下的提示行号是否依然正确且不会引发程序异常。
