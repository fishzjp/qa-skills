# 在线文档协作 测试流水线执行方案

> 本方案遵循 QA 编排流水线规范，规划从需求理解到收尾报告的完整执行路径。单轮交付，不实际执行测试。

## 1. 概述

- **项目名称**: 在线文档协作
- **测试目标**: 端到端验证在线文档协作核心功能，产出最终测试报告。
- **输入材料**: 需求摘要《在线文档协作》、环境与约束说明。
- **缺失输入**: 完整 PRD（仅摘要）、性能指标、浏览器兼容性矩阵、账号批量注册方式。
- **运行约束**: 单会话顺序执行（无子 agent），落盘文件衔接。
- **预算**: 人工 + 自动化混合（自动化方案需裁决）。
- **引用规范**: `evidence.md`（证据体系）、`clarify-pattern.md`（澄清格式）、`report-template.md`（报告模板）。

## 2. 流水线阶段规划

### 阶段 0（旁路）：探索先行
- **Skill**: `exploratory-testing`
- **触发条件**: 需求为摘要，系统陌生。**强烈建议开启**。
- **输入**: 测试环境 URL、测试账号。
- **输出**: `{项目}/探索笔记_系统陌生探索.md`
- **执行方式**: 快速探索文档协作核心 UI 与交互，产出系统理解与初步风险清单，作为阶段 1 输入。
- **用户决策**: 是否执行本阶段。

### 阶段 1：需求理解
- **Skill**: `requirement-analysis`
- **输入**: 需求摘要、探索笔记（可选）。
- **输出**: `{项目}/需求模型.md`（含业务规则、证据标注、`open_questions` 澄清记录）。
- **执行方式**: 建模角色权限、链接分享状态机、协作编辑策略、版本历史机制、评论与 @ 流程。按歧义九类模型扫描材料。
- **检查点（⏸ 澄清检查点）**: 向用户呈现 `open_questions` 待裁决。问题清单已汇总至本文档 §4「待澄清清单」，用户裁决后更新 `{项目}/需求模型.md`。

### 阶段 2：测试策略
- **Skill**: `test-strategy`
- **输入**: `{项目}/需求模型.md`
- **输出**: `{项目}/测试策略.md`（Risk Map + Scope + Type Scope）、`专项移交_{轴}_{日期}.yaml`（如有 handoff/blocked 轴）
- **执行方式**:
    1. **Risk Map**: 并发编辑冲突、权限逃逸、分享泄露、版本数据丢失、性能瓶颈。
    2. **Scope 定义**: 功能域（权限/分享/协作/评论/版本）、非功能域（性能/兼容性/安全）。
    3. **Type Scope 决策**:

        | 轴 | 决策 | 理由 |
        |---|---|---|
        | functional | include (full) | 核心功能，需全面覆盖 |
        | api | include | 权限与分享接口 |
        | security | include | 权限逃逸高风险 |
        | performance | blocked | 指标空缺，需用户澄清 |
        | compatibility | include | 主流浏览器 |

    4. **预算提案（⏸ 预算裁决）**:
        - 自动化（60%）：P0/P1 核心路径，E2E（Playwright）+ API 测试。
        - 手动（40%）：探索式测试、复杂并发场景、兼容性测试。
- **用户决策**: 1. 预算分配方案是否接受？ 2. 性能测试是否纳入 scope？（若否，显式排除）

### 阶段 3：用例编写
- **Skill**: `test-case-writing`
- **输入**: `{项目}/测试策略.md`
- **输出**: `{项目}/测试用例_markmap.md`、`{项目}/测试用例.schema.yaml`
- **执行方式**: 按优先级（P0, P1, P2）编写，双轨落盘（Markmap 可视 + Schema 结构化），产出附录缺陷记录与高风险点。
- **用户决策**: 无需暂停。

### 阶段 4：用例审查
- **Skill**: `test-case-review`
- **输入**: 阶段 3 产物。
- **输出**: 修订后用例文件 + 审查记录（含独立审查落款）。
- **执行方式**: 审查完整性、一致性、可执行性，重新抽取 Schema 校验。
- **用户决策**: 无需暂停。

### 阶段 5：执行
- **Skill**: `automated-e2e-testing` / `api-testing` / manual
- **输入**: 测试用例、测试环境、自动化脚本。
- **输出**: `测试报告_{来源}_{日期}.md`（自动路径）或 `手动执行记录_{日期}.md`（手动路径）
- **执行方式**:
    1. **自动化提案（⏸ 执行策略裁决）**:
        - E2E（Playwright）：P0 核心路径（登录、创建、协作、分享、评论、回滚、权限变更）。
        - API（Python requests）：权限 API、分享 API、版本历史 API。
        - 手动：探索式测试、复杂并发场景、跨浏览器兼容性、UI 细节。
    2. 执行并回收结果。手动路径需用户填写 TC × 结果并回收。
- **用户决策**: 确认自动化方案与手动执行范围。

### 阶段 6：Bug 分析
- **Skill**: `bug-analysis`
- **输入**: 执行报告 Bug 清单。
- **输出**: `{项目}/Bug条目_{日期}.md`（含根因分析、影响范围、Severity 依据、修复建议、回归建议）。
- **执行方式**: 对已确认 Bug 进行根因分析（E2/E3 证据），标注影响范围。无 Bug 则记录跳过。
- **检查点（⏸ Bug 定性检查点）**: 对预期 vs 缺陷有歧义的 Bug 向用户定性。
- **用户决策**: 确认 Bug 定性。

### 阶段 7：回归验证
- **Skill**: `regression-testing`
- **输入**: Bug 修复、代码变更。
- **输出**: `{项目}/回归清单_{日期}.md`
- **执行方式**: 确定回归范围（P0 必须 + P1 建议），执行回归，同步 Bug 状态。
- **用户决策**: 无需暂停。若无变更，记录跳过。

### 阶段 8：收尾报告
- **Skill**: `qa`（按 `report-template.md`）
- **输入**: 所有阶段落盘产物。
- **输出**: `{项目}/测试报告_{日期}.md`
- **执行方式**: 汇总概览、执行统计、Bug 清单（拼装 Bug 条目）、风险残留、回归摘要、类型域专项结果归一化、机读摘要片段。
- **用户决策**: 交付最终报告，汇报进度与未闭环事项。

## 4. 待澄清清单

> 以下为需求理解阶段识别的模糊项，需用户在流水线执行前裁决。裁决后更新至 `{项目}/需求模型.md` 的 `open_questions` 节。

**1. 🔍 需求澄清：并发编辑冲突策略**
- **来源**: 需求摘要「协作编辑」节
- **具体问题**: 多 editor 同时编辑时，系统自动合并的具体冲突解决策略？是否出现冲突提示？用户是否需要手动解决？
- **影响**: 核心 P0 用例设计（协作编辑的正确性验证）。
- **建议选项**: A) 自动合并，无冲突提示（类似 Google Docs）；B) 自动合并，有冲突记录；C) 段落锁机制。

**2. 🔍 需求澄清：版本历史保留与回滚可撤销**
- **来源**: 需求摘要「版本历史」节
- **具体问题**: 1) 保留最近 50 个版本：是否包含当前版本？超 50 删除最早还是阻止新版本？ 2) "回滚可撤销"：回滚是创建新版本，还是撤销回滚操作本身？
- **影响**: 版本历史模块的边界用例与回滚流程设计。
- **建议选项**: A) 保留最近 50 次操作，超出自动删除最早；B) 保留 50 个版本点，超出锁定；C) 回滚即创建新版本，可再次回滚；D) 回滚操作本身可撤销（类似 Ctrl+Z）。

**3. 🔍 需求澄清：链接分享「仅邀请者」与「关闭」的语义**
- **来源**: 需求摘要「链接分享」节
- **具体问题**: 「仅邀请者」是否等同于通过链接分享关闭，但保留邀请入口？「关闭」是否意味着链接彻底失效？
- **影响**: 分享状态机建模与权限测试用例。
- **建议选项**: A) 四种状态互斥，分享粒度不同；B) 「仅邀请者」是「关闭」下的一种子状态。

**4. 🔍 需求澄清：性能指标（NFR 空缺，最大风险）**
- **来源**: 需求摘要「性能」节
- **具体问题**: PRD 未给出任何性能指标与并发规模要求。本次测试是否需要验证性能？若需要，预期并发用户数、文档大小、响应时间阈值、吞吐量指标是多少？若无指标，性能测试不可测，建议显式排除在本次 scope 外。
- **影响**: 测试策略的 Type Scope 决策（included / excluded / blocked）。
- **建议选项**: A) 本次不验证性能（排除在 scope 外，记入非目标）；B) 需要验证，请提供具体指标。

**5. 🔍 需求澄清：浏览器兼容性基线**
- **来源**: 环境约束
- **具体问题**: 需要覆盖哪些浏览器及其版本？
- **影响**: 兼容性测试用例范围与执行环境搭建。
- **建议选项**: A) 仅测试 Chrome 最新版；B) 覆盖 Chrome/Firefox/Safari/Edge 最新版；C) 请提供正式兼容性矩阵。

**6. 🔍 需求澄清：角色模型与权限变更**
- **来源**: 需求摘要「角色与权限」节
- **具体问题**: 1) owner 是否只能有一个？是否可以转让？ 2) 角色变更的生效方式（即时生效 / 刷新后生效 / 存在延迟）？
- **影响**: 权限测试用例设计。
- **建议选项**: A) 不可转让；B) 可转让，转让后原 owner 降级为 viewer。

**7. 🔍 需求澄清：评论与 @ 功能细则**
- **来源**: 需求摘要「评论与 @」节
- **具体问题**: 1) @ 用户通知渠道（仅站内通知 / 邮件 / 短信）？ 2) 评论是否可以编辑或删除？是否支持富文本？ 3) @ 用户是否有自动补全提示？
- **影响**: 评论功能测试用例设计。
- **建议选项**: A) 仅站内通知，评论不可编辑/删除；B) 站内+邮件，评论可编辑。

**8. 🔍 需求澄清：测试账号与数据准备**
- **来源**: 环境约束
- **具体问题**: 现提供 4 个角色账号。若需要模拟多人协作（>4 人）或大量数据，如何获取更多账号？是否有注册接口或批量创建工具？
- **影响**: 执行阶段的数据准备方案。
- **建议选项**: A) 无批量创建工具，需手动注册；B) 有注册 API 可调用。

**9. 🔍 需求澄清：异步通知时限**
- **来源**: 需求摘要「评论与 @」节
- **具体问题**: 站内通知的时效性要求？多久内必须送达？
- **影响**: 异步通知的测试判定标准。
- **建议选项**: A) 无明确时限，视为即时；B) 请提供 SLA。
